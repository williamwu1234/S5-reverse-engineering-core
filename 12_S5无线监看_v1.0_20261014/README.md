# DC-S5 无线监看 v1.0

**给 Panasonic DC-S5 用的手机 / 电脑无线监视器。**

官方 LUMIX Flow 不支持 S5，本项目把它的核心能力补了回来：
实时取景、触摸对焦、拍照录像、AE 锁定 —— **零依赖、不装 App、浏览器直接用**。

- 纯 **Python 3 标准库**，无需 `pip install` 任何东西
- 界面是单个 HTML 页面，手机/平板/电脑均可访问，可「添加到主屏幕」当 App 用
- macOS / Linux 均可运行

> 📖 **详细用法**：[`使用说明.md`](使用说明.md) ·
> **协议细节与实测数据**：[`附_技术参考.md`](附_技术参考.md)

## ⚡ 三步开始

1. **确认网络** —— 相机接入 Wi-Fi（或手机热点），电脑与相机在**同一网络**。
   验证：`ping 192.168.x.x`（换成你的相机 IP）
2. **启动** —— 双击 `启动.command`（macOS），或命令行 `./run.sh 192.168.x.x`
3. **打开浏览器** —— 访问终端打印的 `http://<本机IP>:8080`

```bash
./run.sh <相机IP> [端口] [节奏模式] [帧率]

./run.sh 192.168.x.x                 # 默认 8080 端口、固定 18fps
./run.sh 192.168.x.x 8090            # 换端口
./run.sh 192.168.x.x 8080 fixed 12   # 降至 12fps 省带宽
```

| 参数 | 默认 | 说明 |
|---|---|---|
| 相机IP | `192.168.54.1` | 相机地址（默认值为相机 SoftAP 网关） |
| 端口 | `8080` | 本机 HTTP 端口 |
| 节奏模式 | `fixed` | `fixed`=固定帧率取最新帧；`adaptive`=跟随相机速率（不推荐） |
| 帧率 | `18` | fixed 模式输出帧率（官方 640p 标准） |

## ⚠️ 三条铁律

1. **不要反复重启本服务** —— 每次启动都会重新向相机申请授权，会话正常后就一直用着
2. **不要短时间狂点按钮** —— 相机对控制命令频率敏感，连点会被拒绝一段时间（等几秒即可）；
   工具已内置退避重试与 3Hz 限流
3. **相机提示 `invalid login` 时，只能给相机断电重启**（拔电池 10 秒）

# v1.1 新增：LUT 实时套用 + 机身存储访问诊断

## 一、LUT 实时套用（`s5_lut.py` + 网页「🎨 LUT」面板）

**为什么做在这一层**：初代 S5 **机内没有 Real Time LUT**（影像管线里没有实时 3D LUT 级），
所以"机内烧录"不可能。但相机的**实时取景流**是 WiFi 上唯一真正实时、且本工具已跑通的图像通道
——把 LUT 套在这一层，就得到**实时套 LUT 的画面**。

| 项 | 实测 |
|---|---|
| 支持格式 | Adobe/Resolve `.cube`（3D 浮点）与 Panasonic `.vlt`（整数 0–4095，两种轴序） |
| 单帧耗时 | **20–26 ms**（640×432），取景流有余量 |
| 正确性校验 | `.cube` 与 `.vlt` 两条路径**逐像素最大差 = 1**（仅量化取整） |
| 使用 | 浏览器 → 「🎨 LUT」→ 选文件 → 勾选「启用」→ 取景即套上 LUT |

> **踩过的坑（已修）**：`.cube` 规范是 **R 变化最快**，而 numpy 的 C-order reshape 让最后一个下标最快
> ⇒ 直接 `reshape(N,N,N,3)` 得到的是 `[b,g,r]`，必须 `transpose(2,1,0)`。
> 该 bug 由"`.cube` 与 `.vlt` 结果必须一致"这条验收标准抓出。

自带 5 个 LUT（`lut/`，由 `make_lut.py` 按公开规范生成）：
`vlog_to_709_17.vlt` / `_altAxis.vlt` / `_17.cube` / `_33.cube` / `_33.vlt`。

> 顺带发现：**17³ 与 33³ 网格在暗部差异可达 126** —— V-Log 曲线暗部很陡，17³ 不够用。
> 机身只吃 17³，但**实时监看可以用 33³**，画质更好。

## 二、机身存储访问诊断（`s5_content.py` + 网页「📁 机身存储访问」）

`/api/content_diag` 会把**所有可能影响放行的因素**逐项测一遍，包括一个极易被忽略的状态。

### 已从官方 APK 取出的确切 DLNA 请求（`p168v5/a.java:212-213`、`p168v5/m.java:83-87`）

```
URL      : http://<ip>:60606/Server0/CDS_control
Headers  : Accept-Charset: UTF-8
           Content-Type: text/xml; charset="utf-8"
           SOAPAction: urn:schemas-upnp-org:service:ContentDirectory:1#Browse
           User-Agent: Panasonic MIL DLNA CP UPnP/1.0
           Host: <ip>:60606
Body     : 单行无空白；子元素**不带 s: 前缀**；含松下私有扩展
           <pana:X_FromCP>LumixLink2.0</pana:X_FromCP>
           xmlns:pana="urn:schemas-panasonic-com:pana"
```

### ★ 实测结论（2026-10-14）

| 检查 | 结果 |
|---|---|
| `getstate` / `getinfo camsetting` | **`err_reject`**（相机处于拒绝服务状态） |
| `accctrl&type=req_acc` | **`err_others_requesting`** ← **关键** |
| `get_content_info&value=0/1` | **`err_reject`**（★**端点存在**但被拒；不是 `err_param`） |
| DLNA 静态资源（设备描述 / SCPD） | HTTP **200** |
| DLNA 控制面（Browse，**逐字节官方请求**） | HTTP **403** |

### 两个层次的原因（重要）

1. **状态层**：`err_others_requesting` = 相机端**有一个"别的客户端正在请求"占用了唯一的待批复槽**
   （本项目 `01_研究报告/18_…:120` 记载「相机端**只有一个『待批复』槽**」）。
   它会让 `getstate` / `getinfo` / `get_content_info` **一律回 `err_reject`**。
   ⇒ **在相机屏幕上处理那个待批复对话框（允许或拒绝）**，或重启相机清掉陈旧请求。
2. **通道层**：即使状态正常，DLNA **控制面**仍返回 403（静态资源却 200）
   ⇒ 相机对 DLNA 控制做了**单独限制**，且**不是请求格式问题**（官方请求逐字节复刻仍 403）。

### 可选的下一步（按代价排序）
- 切到相机 **SoftAP 模式**（手机同款路径）重测 DLNA；
- 检查相机菜单里的 **Wi-Fi → 发送图像 / DLNA 服务** 是否需手动启动；
- 走 **USB（Tether/存储）或读卡器**，用 `watch_bake.py` 批量烧（不依赖任何网络门）。

### 关于蓝牙（已排除）
本项目 `01_研究报告/20_…` 已实测：**BLE 身份注册成功，但打不开 WiFi 的 accctrl 门**（两道门独立）；
BLE 只暴露凭据面（SSID/密码特征），**没有文件传输面**，吞吐 ~10–100 KB/s 量级
⇒ 传照片都不现实。

# ⛔ 操作铁律（踩过坑，务必先读）

## 1. `req_acc` 绝不能高频重发

相机对 `accctrl&type=req_acc` 有**频率保护**：

```
短时间多次 req_acc  ⇒  相机屏幕显示「智能手机应用程序需要更新」
                    ⇒  invalid login
                    ⇒  **必须断电重启相机**（只能这样恢复）
```

**症状**：所有端点开始返回 `err_reject` / `err_unsuitable_app`，`startstream` 被拒（画面完全不动）。

## 2. 三条必须遵守的规则

| # | 规则 | 原因 |
|---|---|---|
| 1 | **`req_acc` 只在启动时发一次**，之后只轮询 `getstate` 心跳保活 | 心跳就是会话保活机制；多发 `req_acc` 会触发频率保护 |
| 2 | **会话拿到 `ok` 后不要重启本服务** | 重启 = 重新请求 = 需重新批准，且累积触发保护 |
| 3 | **清理陈旧 pending 必须用同一 UUID**，且 `err_others_requesting` 时不要清理 | 相机端只有一个"待批复"槽；用错 UUID 或误伤他人请求都会污染状态 |

## 3. 不要用裸 `curl` 直接访问相机

```bash
# ❌ 危险：不带 value（UUID）的 req_acc 会留下**匿名 pending**，
#          之后监视器带正式 UUID 请求时会撞上它 ⇒ err_others_requesting
curl "http://<相机>/cam.cgi?mode=accctrl&type=req_acc"
```

相机的访问控制是**按客户端身份**的，**同一个时刻只有一个身份能用**：
监视器持有 `ok` 时，裸 `curl` 一律返回 `err_unsuitable_app`（**这是正常的，不是故障**）。
⇒ **所有操作都走监视器的 HTTP API（8080），不要绕过它直接打相机。**

## 4. 恢复流程（出现 invalid login 时）

```
① 相机断电重启（拔电池几秒再上电）—— 这一步不可省
② 确认在线：curl -s -A "LUMIX Sync" "http://<相机>/cam.cgi?mode=getstate"  → <result>ok</result>
③ 启动本工具【一次】，然后**不要再碰相机**
④ 通常 10–20 秒内 accctrl 变 ok（顶栏显示）
```

**实测**：干净状态下本工具**10 秒**即拿到 `ok`，取景流 30 fps。

## 5. 性能教训（给改代码的人）

**实时 LUT 必须在真实分辨率上测性能。**

本项目曾用 320×240 合成图测出 20–26 ms，就以为 18 fps 够用；
但真实取景流是 **640×360（3 倍像素）**，实测 **73–160 ms/帧**，远超 55.6 ms 预算
⇒ 队列空、反复重播上一帧 ⇒ **画面看起来完全卡死**。

修复方式：把 N³ 浮点 LUT 预计算成 **256³ uint8 精确查表**
（输入是 8-bit JPEG ⇒ 颜色空间只有 256³ 种取值，一次预计算即可消除逐帧插值，
结果与原逐帧三线性**逐位等价**，已用全色域随机图 + 8 个角点验证，最大差 0）。

| | 逐帧三线性 | 256³ 查表 |
|---|---|---|
| 单帧耗时（640×360） | 73–160 ms | **6.7 ms** |
| 吞吐影响 | 卡死 | **零损失**（17.4 → 17.8 fps） |
| 构建耗时 | — | 4.7 s（一次性，select 时） |
| 内存 | — | 50 MB |

# ✅ 无线访问机身存储：已解决（2026-10-14 实测定因）

## 一句话

**`accctrl=ok` + 相机切到【回放模式】⇒ DLNA 立刻列出全部内容，可从 50001 端口下载原始全分辨率照片。**

## 三个必要条件（缺一不可）

| # | 条件 | 说明 |
|---|---|---|
| 1 | **`accctrl` 达 `ok`** | 未达时 `POST /Server0/CDS_control` 一律 **403**；达到后才会处理请求 |
| 2 | **相机在【回放模式】** | ★ 这是卡了最久的一环。**拍摄模式下内容树是空的**（`NumberReturned=0` 或 701），切到回放后立刻返回 16 个条目 |
| 3 | 用**官方逐字节的 SOAP 格式** | 见下 |

切回放模式一条命令：`camcmd&value=playmode`（本工具的 `/api/gallery` 已**默认自动切**）。

## 官方请求格式（从 APK 取出，`p168v5/a.java:212`、`p168v5/m.java:83-87`）

```
URL      : http://<ip>:60606/Server0/CDS_control
Headers  : Accept-Charset: UTF-8
           Content-Type: text/xml; charset="utf-8"
           SOAPAction: urn:schemas-upnp-org:service:ContentDirectory:1#Browse
           User-Agent: Panasonic MIL DLNA CP UPnP/1.0
           Host: <ip>:60606
Body     : 单行无空白；子元素**不带 s: 前缀**；含松下私有扩展
           <pana:X_FromCP>LumixLink2.0</pana:X_FromCP>
           xmlns:pana="urn:schemas-panasonic-com:pana"
```

## 响应长什么样

`NumberReturned=16`，每条 item 含**三种分辨率**：

```xml
<item id="01000018" parentID="0">
  <dc:title>100-0018</dc:title>
  <upnp:class name="imageItem">object.item.imageItem</upnp:class>
  <res ...DLNA.ORG_PN=JPEG_LRG... size="9346560">http://<ip>:50001/DO01000018.JPG</res>  ← 原图
  <res ...DLNA.ORG_PN=JPEG_MED... size="100000"> http://<ip>:50001/DM....JPG</res>      ← 中图
  <res ...DLNA.ORG_PN=JPEG_TN ... size="5000">   http://<ip>:50001/DT01000018.JPG</res>  ← 缩略图
</item>
```

**⇒ `50001` 端口就是内容数据服务**（此前项目报告 18 说它"家网侧不存在"，
实测**存在且未识别**，现在确认它就是图片/视频的下载端口）。

## 走过的两个弯路（留给后来人）

| 弯路 | 真相 |
|---|---|
| 「相机对 DLNA 控制做了单独限制」 | 其实只是 `accctrl` 没到 `ok`。**403 是授权问题，不是 DLNA 特有限制** |
| 「内容树为空 = 卡上没照片」 | 拍了 4 张照片后**仍是空的**。真正原因是**相机不在回放模式** |

## 另一个坑：DIDL 是 HTML 转义的

SOAP 把 DIDL 放在 `<Result>` 里**转义**了（`&lt;item id=&quot;...&quot;&gt;`）。
直接对原文做正则会得到 **0 条目**，从而误判为"内容树为空"。
**必须先 `html.unescape()`**（`s5_content.parse_items()` 已修）。

| 项 | 结果 |
|---|---|
| 授权耗时 | **10 秒**（干净状态） |
| 内容条目 | **16**（15 JPEG + 1 MP4） |
| 下载原图 | **9,346,560 B** = 6000×4000 MPO |

# ⚠️ 相册与取景互斥（卡顿的真相）

## 现象与定因

用过「列举相机内容」后，实时取景出现明显卡顿（诊断面板显示相机侧空档 700–880ms）。

**定因（三层）**：

1. **取片的必要条件**：DLNA 内容树**只在回放模式下有内容** ⇒ 列举必须先切 `playmode`
2. **回放模式下没有实时取景** ⇒ 相机只会零星推帧 ⇒ 画面卡顿
3. **原实现切过去就不管了** ⇒ 相机一直停在回放模式 ⇒ 取景持续卡顿

## 修复

`/api/gallery` 与 `/api/download` 办完会在**后台线程自动 `camcmd recmode`** 切回拍摄模式
（`?restore=0` 可关闭）。界面上也加了提示。

## ★ 怎么正确判断"是否还在卡"

诊断面板的 `max_camera_gap_ms` 是**累计值**——它会把「流重启时的一次 10.7 秒空档」
和「回放模式期间的零星推帧」永远算在里面，**看起来像是一直没修好**。

**应看近期窗口**，别信累计最大值：

```bash
# 每 250ms 采一次帧计数，连采 20 秒
python3 - <<'EOF'
import urllib.request, json, time
def st():
    with urllib.request.urlopen("http://127.0.0.1:8080/api/state", timeout=5) as r:
        return json.load(r)
prev = st()['frames']; t0 = time.time(); s = []
while time.time() - t0 < 20:
    time.sleep(0.25); f = st()['frames']; s.append(f - prev); prev = f
run = mx = 0
for x in s:
    if x == 0: run += 1; mx = max(mx, run)
    else: run = 0
print(f"{sum(s)/20:.1f} fps   空窗口 {sum(1 for x in s if x==0)}/{len(s)}   最长空档 {mx*0.25:.2f}s")
EOF
```

**健康标准**：18 fps 左右、250ms 窗口均匀 4–5 帧、空窗口 0、最长空档 0.00s。

## 另：链路质量是外部因素

实测到**路由器** RTT 3.6/5.4/16.0ms（stddev **2.8ms**，极稳），
到**相机** RTT 7.4/232/743ms（stddev **254ms**）⇒ 抖动来自**相机侧无线链路**。
相机是 2.4GHz-only，若与路由器距离远/隔墙，取景帧率会明显下降——
这属于环境因素，软件层无法根治（可用 `--pacing-fps` 调低目标帧率让节奏更稳）。

顺带排除：ClashX 代理的 `ExceptionsList` 含 `192.168.0.0/16`，**局域网流量绕过代理**，与本问题无关。

## 关于取景卡顿（2026-10-14 定位）

现象：画面看起来一顿一顿。实测**帧间隔中位 56ms、>200ms 停顿 0 次**（时间轴完全平滑），
但**30 帧里只有 15 帧是新画面（重复率 50%）**。

根因：**相机是突发式推流**——诊断面板同时出现 `pacing_underrun=1369`（队列空、垫帧）
与 `frames_dropped_queue_full=1540`（队列满、丢帧）。节奏器把时间轴抹平了，
但抹不平"**相机每秒只给约 9–10 个新画面**"这一事实。

⇒ 这是**相机侧行为**（低照度降帧 / 无线链路），软件层无法根治。
可调项：`--pacing-fps` 调低目标帧率可减少重播比例，但换不来更多新画面。

# ★★ 流畅配置与三条铁律（2026-10-14 定因）

## 一、卡顿的真正来源是【网络路径】，不是参数

**同一台相机、同一套参数（`fixed / 18fps / 队列3`），只换网络路径：**

| 指标 | **相机热点直连** | 经家用路由器 |
|---|---|---|
| 收帧节奏 | 18.1 fps，空窗口 **0/79**，最长空档 **0.00s** | 18.1 fps，空窗口 0 |
| 帧间隔 | 中位 **56ms**，max 59ms，>200ms **0 次** | 同样平滑 |
| **新画面占比** | **40/40 = 100%（重复率 0%）** ✅ | 18/30（**重复率 40%**）❌ |
| **端到端延迟** | **53 ms** ✅ | **400–700 ms** ❌ |
| RTT stddev | **6.6 ms** | **258 ms**（差 39 倍）|

⇒ **时间轴两边都平滑，但经路由器时相机每秒只给 9–11 个新画面**，节奏器只能重播补到 18fps
⇒ 看起来一顿一顿 + 延迟高。**换到热点直连，重复率直接归零。**

**`run.sh` 默认相机地址 `192.168.54.1`（热点网关）不是随便写的 —— 那才是官方设计的低延迟路径。**

## 二、★ 三条铁律（否则会话建不起来）

1. **永远只用监视器自己那一个 UUID**：`4D454930-0100-1000-8001-020A0003BD13`
2. **绝不在启动时发 `req_acc_can`** —— 清理只在【结束】时做
3. **绝不用新 UUID / 匿名请求做调试**

### 为什么（相机维护"已注册设备表"）

| 请求 | 结果 |
|---|---|
| 已注册 UUID | ✅ 直接受理（`ok` / `ok_under_research_no_msg`） |
| **全新 UUID** | ❌ 创建"待批复"请求 ⇒ 之后**所有**请求都看到 `err_others_requesting` |
| **匿名（不带 `value`）** | ❌ 同上，同样污染 |

相机端**只有一个"待批复"槽**。一次没被清理的新请求会**卡住整个会话**，
而且症状很迷惑（`err_others_requesting` 看起来像"别的设备在连"，其实可能只是自己刚才的调试请求）。

## 三、另一个真 bug：SSDP 公布错误的网卡地址

`SSDPAdvertiser._detect_ip()` 原本硬编码：

```python
s.connect(("192.168.1.1", 80))     # ← 写死了家庭路由器
```

本机同时有有线（家网 `192.168.1.x`）与无线（相机热点 `192.168.54.x`）时，
它会公布 `192.168.1.148` —— **相机在热点网段根本够不到**，
表现为：**相机能看到我们的 SSDP 广播，却始终连不上（卡在"选择设备"）**。

**已改为按【相机地址】探测路由**（热点优先、家网兜底）。实测公布地址由
`192.168.1.148` → `192.168.54.10`（相机可达）。
